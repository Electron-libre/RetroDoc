# Crate: retrodoc-pipeline

Detail moved out of `CLAUDE.md`. Pipeline overview: `docs/ARCHITECTURE.md` §4 and §5.

- **retrodoc-pipeline**: orchestrates the multi-pass generation pipeline of `PLAN.md` §2, one module per
pass. The `//!` doc of each module is the reference for what the pass does and why; this is only the map.
`generate` runs them in this order: surface (roles → glossary → entry points), actors, file budget, repo
map, domains, features, use cases, diagrams, business-language score, confidence, then render.

| Module | Role |
|---|---|
| `roles/` | One LLM call over the file tree + manifests: stack, glob rules `pattern -> role`, `source_extensions` (languages the walker doesn't know, promoted to `Source`), plus per-language `chunk_boundaries`. `roles.yaml` is hand-editable and reused unless `retrodoc roles --force`; `RoleRules::classify` applies it mechanically. |
| `sources/` | Where the schema, migrations and translations are, and their format (`retrodoc_ingest::SourceMap`): `SourceMap::sniff` (content, no LLM), then one LLM call over tree + manifests + that guess, rules checked against the real files (`check_rule`; a bad rule is sent back once, then dropped), sniffed sources the LLM missed kept. `signal-sources.yaml` is hand-editable: edited (rules hash differs) it is kept, unedited it is inferred again only when the tree shape changes or with `force`. An LLM failure leaves the sniffed map. |
| `brief/` | The product brief (ADR 0019): one LLM call over a bounded sample of the signals of `retrodoc_ingest::signals` (`sample.rs`: budget per kind, ids `S1`.. the LLM cites, resolved to origins; unknown citations dropped, a claim with none reads as unsupported) writes purpose, users, objects, capabilities, external systems and open questions. `product.yaml` is hand-editable: edited (content hash differs) it is kept, untouched it is reused while the sample is the same (commits left out of that hash), `force` writes it again. `ProductBrief::prompt_section` / `fingerprint` are what the later passes will read. `generate` runs first: the saved brief as it is, or one written now when there is none (`retrodoc brief [--force]` is how it is refreshed). It heads the prompts of `roles` (not in its reuse: the saved rules stay), `glossary`, `entry_points`, `actors`, `domains`, `features` and `use_cases` (its fingerprint is part of their reuse, per unit for the last two; an empty brief changes nothing). `Evidence` (`evidence.rs`), only with `brief.evidence = true` in `retrodoc.toml` (off by default, benchmarks showed fewer features and no gain: `issues/brief_injection_experiments.md`), is what `generate` also keeps of the signals: per feature (use cases) or domain unit (features), the doc sections, test descriptions and commit subjects whose words are closest to the unit's names, description and files (`Bm25::search_any`, about 1,200 / 900 / 900 characters), put in its prompt and in its fingerprint, so a new commit about a unit redoes that unit alone. The standalone commands read the saved brief. |
| `contexts/` | The map of the bounded contexts (ADR 0029, `issues/done/business_files_cap_on_large_application.md`): `groups.rs` groups the source files around the names of the entry point files with no LLM call (`mechanical_groups`, `name_words`), `mod.rs` asks one call to merge the groups into contexts, set the technical ones aside as support and place the orphan folders (a forgotten group is a context of its own, an unreadable answer is one context per group and not saved). A context of more than 150 files is split by one more call into sub-contexts (`split_large_contexts`, up to twice for a part still over the limit and with at least three groups and folders to cut; a big folder is listed by its own sub-folders as deep as it stays big, so that a business family laid out as a folder is a unit of the split; the orphan files of the context that share a name across layer folders (`rules/<family>.rb`, `processes/<family>/`, `tasks/<family>_task.rb`) are listed as groups of their own (`groups::family_groups`: a name in 2 to 8 folders and at least 3 files, not a layer folder, a generic stem, a step every family repeats or an existing group; measured by `context_map_measure --families`), kept in `contexts.yaml` as plain group names that `resolve` finds again, so the split cuts by family and not by layer; what the answer forgets stays with the first part and the context's folders stay only where no part holds them; an unusable split keeps the context whole). `contexts.yaml` (hand-editable, reused until `retrodoc contexts --force`) keeps rules, not file lists: `ContextMap::resolve` finds the files of each context again from the current tree. `run.rs` (`plan_run`, `mark_done`, step 4b): the contexts of a run (named, else the next ones not done within a budget of files, never cutting one) and the files read for them (business roles plus the business files their entry points reference at depth 1 that no other context owns); a context is done while the hash of its files kept in `fingerprints.json` still matches. `domains.rs` (`domains_from_contexts`, `domain_vocabulary`, step 4c): a context is a domain with no LLM call (`DomainCluster::by_paths`: its entry points are those of its files, not those of a shared resource, except the routes: a route goes to the context that owns the entry point file it names, found by file name only, with no framework convention, `route_owner.rs` `EntryOwners`, `DomainCluster::routed_in` / `routed_out`; a route naming a word of its own file's name, or a name two contexts own, stays with its file; a route served by a context out of the run is left out of the run's domains and comes back when that context is run; `cargo run -p retrodoc-pipeline --example route_owner_measure` measures it on a saved run), with its own entities and vocabulary. With `Retention::Others`, `build_features_from_surface` keeps the features and fingerprints of the domains not in the run and places the unclaimed entry points domain by domain (into a feature of their own domain only, one print per domain in `entry_point_placements`, so a domain already placed is never asked again whatever the others of the run are), and `UseCaseContext::domain_vocabulary` keeps the prompts and fingerprints of a context from changing when another one is read (`two_runs_tests.rs`: the second run does not redo nor change the first). Read a context at a time, the business-language score is computed once per use case (`score_unscored_business_language`): the vocabulary known grows with every context and rescoring would change the earlier ones. Read by `generate` when `domains_from = "contexts"` (`crates/retrodoc-cli/src/commands/generate/contexts.rs`). |
| `business_files/` | Where the business lives (`issues/done/locate_business_files.md`): one LLM call over the tree, the stack, the brief and cheap evidence (per directory: files, commits, most changed names; doc titles; test vocabulary) answers a ranked, bounded list of files and directories with a reason (`BusinessMap`, paths that are no source dropped). `business-files.yaml` is hand-editable: edited (content hash differs) it is kept, untouched it is reused while the tree shape and the brief are the same, `force` asks again. `BusinessMap::files` expands it to at most 60 source files. `generate` runs it right after the roles (stack known) and before the glossary; `retrodoc business-files [--force]` is how it is refreshed. The glossary reads it (`build_glossary`'s `business` list, at most 60 files) instead of the `model` role, and the entry points pass reads it next to the `entrypoint` files. |
| `chunks.rs`, `chunk_check.rs` | Cut long files before a definition the parser found (languages of `retrodoc_ingest::structure`, comment and decorator lines above it kept with it), else before a boundary regex, else a blank line; the roles call is told not to give regexes for the parsed extensions and `chunk_check` drops them without a call; `Splitter::excerpt` for the use cases/confidence passes; `chunk_check` verifies the LLM's regexes on the real files and asks for a fix (a weak first try is an `info`; only a rule dropped for good is a `WARN`). |
| `chunks.rs` (body view) | With `[pipeline] body_lines = N` (experimental, off by default; `RoleMap.body_lines`, set by the CLI) the glossary and entry points passes read only the signature and the first N lines of each outermost method/function body of a parsed language, the rest marked `… (k lines omitted)` (`Splitter::file_chunks`; use cases and confidence excerpts are untouched); it is part of those passes' file hash (`Splitter::keyed`), so changing it redoes them. Measured in `issues/done/tree_sitter_structure.md`. |
| `business_read/` | One reading of the business files for the glossary and the entry points (`issues/done/single_read_per_business_file.md`): one call per batch answers entry points (with outputs) and entities, 5,000-character chunks, written to `glossary.yaml` and `entry-points.yaml` with the per-file hash the two passes compute, so they find those files up to date and read only the rest (entry point files outside the business list, a file the joint answer missed). Needs one model for both passes (else each reads alone). `generate` runs it before the glossary (pass `business-read` in the recap; `[pipeline] business_read = false` skips it, `PipelineConfig`); `retrodoc business-read` runs it alone. The `glossary` and `entry-points` commands are unchanged. |
| `glossary/` | Entities from the business files (LLM, batched by characters; without a business list, from the `model`-role files, ADR 0025), test-block descriptions from `test`-role files (mechanical). |
| `entry_points/` | Entry points (`http_route`, `cli_command`, `job`…) with their outputs, from the `entrypoint`-role files and the business files (a file in both is read once; `build_entry_points`'s `business` list, as the glossary's). `EntryPoints::without_unreached_public_api` (`is_application`: a route, job, consumer or webhook entry; a command alone does not make an application, a library often ships one): in an application the `public_api` entries in no file reached (the files of the route, command, job, consumer and webhook entries and their `CodeIndex::slice` at 2 hops) are left out for the later passes, as technical support (`generate` applies it after reading; `entry-points.yaml` keeps them, the choice is made again at each run). A library keeps all its entries. Limits: the reach is by file and by the names the code mentions (a callback or dynamic dispatch is missed), and a `generate` by contexts decides on the entry points read so far. `cargo run -p retrodoc-pipeline --example public_api_reach_measure` measures it on a saved run. |
| `surface.rs` | `Surface::new(glossary, entry_points)`: the capped prompt section that domain clustering starts from (business concepts, never layers); `missing_entities_notice` is the `info` line `generate` logs when source files exist but no entity was found. |
| `actors.rs` | Business actors from authorization code + the glossary entities (the LLM keeps those that stand for someone); `retrodoc actors [--force]`. |
| `ranking.rs` | Optional file budget (`--max-files` / `ingest.max_files`): role × churn × references; the rest becomes `FileKind::Other` (`scope.yaml`). |
| `repo_map/` | File summaries (LLM + git history, cached by content hash, optionally batched/concurrent), then directory summaries bottom-up. |
| `domains/` | One call clusters directory summaries + doc titles + surface into `DomainMap`; `repair.rs` places the files it left unassigned with one small extra call; `coverage.rs` enforces 100% coverage by construction (uncategorized bucket, first assignment wins, hallucinated paths dropped). `from_surface.rs` (`build_domains_from_surface`, ADR 0020) is the other path, with `[pipeline] domains_from = "surface"` in `retrodoc.toml` (default `files`; `PipelineConfig` in `config.rs`): one call groups the resources (entry points by resource) and the entities into flat domains (`DomainCluster.resources` / `entities`), names resolved with `naming::normalize`, first placement wins, unknown names dropped, the rest in `uncategorized`, files attached from the entry-point files and the entity home files; reused while the surface, the brief and the model are the same. In that mode `generate` builds no repo map; the features come from the entry points (`features/from_surface.rs`). |
| `features/` | One call per domain/sub-domain unit (not "uncategorized"), features grounded on a validated subset of its files. `from_surface.rs` (`build_features_from_surface`, `domains_from = "surface"`): one call per domain (flat, the `uncategorized` one too: it can hold most of the entry points of a large application) over the entry points of its resources and its entities; entry points are shown with short tags `E1`.. and cited by tag (the id `<file>#<name>` of `entry_point_id`, or a bare name unique in the domain, also resolve), unknown ids dropped, first placement wins, a feature with none left dropped, a domain whose answer holds no usable feature asked once more, a domain with more than `MAX_ENTRIES_PER_PROMPT` (150) entry points asked in slices of whole files (a file over the limit is cut), one call per slice that shows the features of the earlier slices and may give one again (features of the same slug or name merged: entry points united, first description kept), one print per slice (`<domain>/slice-N` in `fingerprints.json`, the entry points up to the end of the slice) and a save after each slice, so a killed run keeps the slices done (and, for the slices not asked yet, what the previous run had) and a change in a later file asks only the slices from there (known limit: the print of a slice does not cover the answers of the earlier ones, so an earlier slice redone with other names leaves the later ones as they were; the merge by slug or name then takes care of the same names), an entry point held by two features kept by the feature of the domain that owns it; `Feature.entry_points` holds the ids and `source_paths` their files; fingerprint on the entry points, entities, brief, evidence and model, so an unchanged run makes no call. The use cases pass reads exactly `Feature.entry_points` when set (else the entry points of the feature's files). Coverage by construction: `from_surface/repair.rs` then asks (batches of 60, `placements`) for each entry point no feature holds, to join an existing feature; unknown ids and features are dropped; what stays out is saved with the technical support in `behaviour-coverage.yaml`, reused while its input hash (`Fingerprints.entry_point_placement`) is the same. Both prompts ask for `back_office` (an administration tool, used by the people who run the application): read into `Feature.back_office` (absent means false), kept by the reuse of a unit and by the partial redo of a slice (`restricted` clones the feature); the prompt is not part of the fingerprints, so a run saved before this key keeps `false` until `--force`. The docs set such a feature apart (`retrodoc-render`). |
| `use_cases/`, `slices.rs` | One call per feature with numbered code excerpts, entry points and the code they run (`CodeIndex::slice`); steps, actors, `narrative`, `primary_actor`; citations are validated. The prompt shows the kind of each entry point (`[http_route]`, `[job]`…) and asks for no human actor and no `primary_actor` when only a job, consumer, webhook or public method leads to the use case (the check that follows is `without_invented_humans`); it also asks for one use case, citing both entry points, for the route that opens a form and the one that submits it; a feature with more than `MAX_ENTRIES_PER_CALL` (12) entry points is asked in slices of whole files (`file_ranges`, shared with the features pass; a file over the limit is cut), one call per slice one after the other, each with its own tags, prompt and cited files, so no answer is cut at the output limit; the slices are one unit for the fingerprint and the save (a slice with no usable answer leaves the feature to the next run), the slugs are made unique across slices, and a use case is never merged with another; the entry points are shown with tags `E1`.. and each use case cites those it covers (`known_entry_points`: by tag, else by id `<file>#<name>`, else by a name unique in the feature; the unknown and the ambiguous are dropped), `UseCase.entry_points` holds the ids (names in artifacts saved before, not migrated; `UseCase::entry_point_names` is what the docs and the MCP show); the prompt is not in the fingerprints, so saved use cases are not derived again before `--force`. `grounding.rs` `without_invented_humans`: a use case reached only through entry points no person starts (job, consumer, webhook, public method; a route, a command or an unnamed kind keep the human; a feature with no entry point is not judged) loses a human primary actor (a known software one stays) and its human steps become the calling program, the external provider or the system. Applied to new answers only: a saved use case keeps its actors until it is derived again. |
| `diagrams.rs` | Deterministic Mermaid `sequenceDiagram` per use case, no LLM. |
| `vocabulary.rs` | Deterministic `business_language` score per use case, recomputed each run. |
| `confidence/` | Mechanical checks first (`checks.rs`, ADR 0026: cited file and lines exist, identifiers and glossary entities a step names are in the cited code): a passing step is supported, one whose cited code is missing is unsupported, none asks the LLM. The LLM gives a verdict only on the doubtful steps (shown with their code) and, with `--confidence-sample N`, on N fully passing use cases as a second opinion. Score capped for ungrounded steps (`--no-confidence`). `mechanical_score` and `examples/confidence_agreement.rs` compare the checks with saved model scores (no LLM). |
| `rules/` | Business rules (ADR 0021, `issues/done/business_rules.md`), `[pipeline] rules = true` (off by default; pass `rules`, after the use cases; `rules.yaml`). No language or framework pattern is hard-coded: the LLM decides what is a rule. `RuleInput` (`input.rs`, no LLM) is what one feature's rules are read from: the same files as its use cases (`FeatureInput`), the glossary entities that code names (as words), and the closest doc sections and test descriptions with their origin (`Evidence::extracts`, commits left out). `build_rules`: one call per feature (numbered code, files cited by their number `F1`.. and a line range as `"F1:10-24"`, evidence by short ids `T1`/`D1`, never by path; the answer is kept short to stay under the completion cap, so the model does not write the entities: they are the glossary names the statement speaks of as whole words), `grounding.rs` keeps a rule only with a code citation on a shown file and lines inside it (a path or the old `{path, start_line, end_line}` object is still read), a quoted test phrase must be in the extract, use cases are those of the list; an answer the server cuts at its completion limit (`CompletionResponse::truncated`, from `finish_reason=length`) is not asked again as it is: `split.rs` asks again on the two halves of the files shown (in the order of the prompt, recursively down to one file), grounds each half against its own file numbers, merges them (a repeated statement kept once, slugs numbered again from 1), and a part that still can't be read leaves the feature to the next run; the cut itself is logged at info (the pass warns when it gives up), the number of rules stated and kept per call too (`rules answer read`), the characters of each answer at debug; confidence 0.4 code alone, 0.7 with a test or a doc, 0.85 with both; rule slug `<feature-slug>-<n>`. Before the rules, `judge.rs` asks one short question on the name and description of the feature alone: is it about how the application is tested? If so it has no rules and no statement call (measured on a large repository, no judgement per rule left such a feature out steadily, this question was right for every feature; an answer that is not a clear yes counts as no). Then, after the rules, a second short call per feature that has rules (statements, kinds and backing only): each rule gets a class, `business` or noise (`storage`, `screen`, `test`, `technical`), and the noise is dropped (logged at info, the slugs of the others keep their number, so a number can be missing). A closed class per rule, not a list to drop: on hand labels of a large repository the list lost 22% of the good rules, the classes 3% for 65% of the noise (`issues/done/rules_deduplication_and_noise.md`). A rule left unclassed is kept; an unparseable verdict keeps all the rules of the feature as stated (the call is logged), and the judgement prompt is part of the feature fingerprint. Last, `dedup.rs` (no LLM) keeps once the rule several features state: two rules of different features are the same when their statements share at least 60% of their words (of more than three letters) and they cite overlapping lines, or share 75% (joined by decreasing similarity, a group never holding two rules of one feature and joined only if every rule of one is alike every rule of the other, so "unknown customer" and "unknown restaurant" stay apart); the copy kept is the one of the feature with an entry point in the cited file, then the one backed by a test or a doc, then the one reading the fewest files, then the first by slug; it takes the entities, use cases, tests, documents and best confidence of the copies it replaces. What a rerun starts from is `rules-stated.yaml` (the rules as each feature stated them, what the fingerprints describe); `rules.yaml`, read by the render, the MCP and the report, is that set once merged, so a copy comes back when its owner stops stating the rule. What the LLM set aside is kept to be checked (`aside.rs`, `rules-set-aside.yaml`): the features taken for tests (they lose every rule, so a wrong answer costs the most) and the rules dropped as noise, each with its class; they come back with the feature when it is reused, and `report.rs` (`with_set_aside`) lists them in the section "Set aside by the rules pass (to check)" of the debt report. A run saved before that file is asked again once, since its fingerprints can't tell a feature about tests from the rest. Fingerprint per feature (text, code, evidence, use cases, brief, the statement, kind and judgement prompts, model: a new answer shape asks the saved features again once); an unchanged feature makes no call, an unparseable answer is retried next run. `retrodoc-render` shows them (`render_with_rules`, `rules.rs`): on the feature page, on the use case pages they apply to, per domain and in `functional/rules.md` (by entity, there is no entity page), with their evidence; none saved gives the same files as before. `retrodoc-mcp` serves them (`Docs::with_rules`, loaded from `rules.yaml`): in `get_feature`, `get_use_case` and `get_domain` with their evidence and a stale warning, as `rule` entries of `search_docs` (id = the rule slug), and the code they cite is readable by `read_source`; no new tool. The debt report reconciles the rules with the project docs like the other items (`reconcile/`). |
| `behaviour_coverage.rs` | `BehaviourCoverage` (`behaviour-coverage.yaml`, `domains_from = "surface"` only): the entry points no feature holds (written by the features pass), with `by_domain` for a `domains_from = "contexts"` run (entry points held and held by no feature, per context, renewed when the context runs; printed by `generate` and listed in the coverage report under "Entry points by context") and the source files reached by no behaviour, `save_technical_support` (files of the documented entry points, their slice, entity files; the rest is technical support), computed by `generate` after the features; and `by_feature`, `save_use_case_coverage`: per feature of the surface, the entry points it holds and those no use case of it cites (by id; use cases saved with names cover nothing until derived again), renewed for the features whose use cases `generate` just derived, printed by `generate` and listed in the coverage report under "Entry points without a use case". |
| `report.rs` | Documentation debt report from the saved artifacts (`retrodoc report`, no LLM); with a saved `BehaviourCoverage` it lists the entry points without a feature and the technical support; with a `Reconciliation` (`with_reconciliation`), the section "Existing documentation": per domain the items documented, matched but not judged, undocumented and contradicted, then the contradictions (both sides cited, a finding to check) and the undocumented items, most entry points first. |
| `reconcile/` | Reconciliation with the project's own docs (`specs/docs-reconciliation.md`, ADR 0033). No LLM (`mod.rs`): every domain, feature, use case and rule is matched by BM25 (name and description, a rule its statement; at least half of the content words; at most 3 sections) against the doc sections of the existing docs, the generated docs left out by the caller (`project_docs`); no section is `undocumented`, a rule citing a doc section is `documented` by it. Pass `reconcile` (`judge.rs`, `[pipeline] reconcile`, on by default, last pass of `generate`): the other matched items go to the LLM 8 at a time, the sections of a request listed once (`S1`..), each section answered `covers`, `contradicts` (with `doc_states` and `item_states`, else no answer) or `unrelated`; `reconciliation.yaml` keeps per item the fingerprint of its text and its sections' text, and the model: an unchanged item makes no call, an item with a section unanswered is not saved (asked again next run). `Reconciliation::new` (read by the report, no model) applies a verdict while the fingerprint matches: one contradiction makes the item `contradicted`, else a cover `documented`, else `undocumented`; no verdict leaves it `matched`. |
| `benchmark/` | Quality benchmark (`issues/done/quality_benchmark.md`, `issues/done/benchmark_spread_and_judge_bias.md`): `Reference` (hand-written `benchmark/<repo>/reference.yaml`, checked on load) and `RunMetrics` (sizes, mean business-language score and the share of use cases at score 1, mean confidence, cost of the last `generate`, read from `.retrodoc/cache/`, no LLM). `Matches` (hand-written `matches.yaml`, wins over the normalized-name match) and `compare` (recall and precision of domains and features, with what is left unmatched). `judge` (LLM proposals for what is left unmatched, rating of narratives; never overrides `matches.yaml`) and `summary` (the text `retrodoc benchmark` prints) and `table` (`RunReport` per run, series per configuration, mean/range/change table). `frozen` (`FrozenInputs`: the artifacts of one good run kept in `~/retrodoc-runs/frozen/<repo>/` with a `manifest.yaml` naming the model and commit; `prepare(ReplayPass, work_root)` copies them without the artifact of the replayed pass and the ones after it, so one pass runs alone on fixed inputs; `issues/done/benchmark_passes_on_fixed_inputs.md`). `replay` (`replay_domains` and `replay_features`: run the surface clustering, or the features pass on the frozen domains (`FrozenInputs::replace_domains` freezes domains clustered from the surface, the ones of the `files` path hold no resources), once on a work directory prepared from `FrozenInputs`, score the domains or the features against the reference strictly and with the pairs the judge proposes, counts the calls and tokens of the pass apart from the judge's; `replay_table`: one row per run, mean and range; `replay_use_cases` runs the use cases pass on the frozen features, reading the code of a copy of the tree, and measures the use cases (`UseCaseFigures`, `use_case_table`); `replay_rules` does the same for the rules pass on frozen features and use cases (`RuleFigures`, `rule_table`: rules stated and kept, rules of the reference a generated rule states by the judge, which sees the 12 closest by BM25); the `pass_replay` example runs a pass N times). |

Cross-cutting pieces: `batched_read.rs` (the loop of the glossary and entry points passes: files in
batches of ~12k chars, an unusable batch retried file by file, a checkpoint after each batch), `artifact.rs` (`Artifact`: the names of everything under `.retrodoc/cache/` and which `generate --force` clears; load/save of those files; a missing or
unreadable file is a first run, not an error), `response.rs` (`complete_text`, and `complete_json` with
the `schemars` schema of its answer type sent as `response_format`, `response_schema` making it strict — every raw answer type derives `JsonSchema`; lenient parsing (fences, prose, a repeated field keeps its last value) and one retry; an unparseable unit is skipped with a warning), `fingerprints.rs` and
`cache.rs` (incremental re-run), `source_hashes.rs` (`source-hashes.json`: the hash of each source file at the last complete `generate`, what MCP freshness compares against), `progress.rs` (one `tracing::info!` line per unit with ETA), `naming.rs`
(the single `normalize` used to match names across passes), `usage_log.rs` (the end-of-run recap text and the
history of the last 20 runs in `.retrodoc/cache/usage.json`), `error.rs`.

Behaviors that span passes:
- **Incremental re-run**: each pass skips a unit whose input fingerprint is unchanged and reuses its saved
  result (features per domain unit, use cases per feature, summaries per file hash, directory summaries per
  listing hash, domains per clustering input; a feature answered "no use case" twice cleanly is remembered too). `generate --force` wipes the caches. The model of the pass (`LlmProvider::model`, `fingerprints::model_part` / `hash_for_model`) is part of what is compared, so another model redoes the pass: domains, features, use cases and actors fingerprints, glossary and entry points file hashes, the `model` of the repo map cache (not in `content_hash`, which the MCP freshness check reads), and `confidence_model` in `fingerprints.json` (another model clears the scores and scores them again, within `--confidence-sample`). The hand-editable `roles`, `sources`, `business-files` and `brief` stay until `--force`.
- **Model per pass** (ADR 0023): `[llm.passes.<name>]` (`PassLlmConfig`, the keys of `[llm]`, names in `config::PASS_NAMES`, unknown name or key = config error) overrides `[llm]` for one pass: `LlmConfig::for_pass`. A pass that changes `provider` without `api_key_env` takes that provider's key variable; an empty `base_url` drops the global one; `batch_chars` is read for `repo-map` only. The CLI's `PassProviders::open` builds one provider per distinct configuration (shared between passes with equal settings, opened before any call so a missing key names its pass), `get(pass)` hands it out.
- **Additive readings**: `build_glossary` and `build_entry_points` take a `Retention`: `OnlyRead` (what `generate`, `glossary` and `entry-points` use today) rebuilds the inventory from the files read now, `Others` also keeps the saved entries of the other files that still exist, which is how a repository is read in several runs, one context at a time (`issues/done/business_files_cap_on_large_application.md`, step 4). The joint reading (`business_read`) already only adds.
- **Resumable**: every pass saves after each answer or batch (the readings, the repo map, the features of
  the `surface` path per domain, the use cases and the rules per feature, the confidence scores per request;
  the units not reached keep their previous results and fingerprints), and an artifact is written beside
  then renamed (`artifact::write`). A run that fails or is killed loses the call in flight; the rerun
  resumes there. The features of the `files` path are saved on an LLM failure only. Tested with
  `FakeLlm::hanging_after` and `testing::killed`.
- **Cost control**: `llm.concurrency` (default 1) parallelizes file and directory summaries and the use cases and confidence passes (requests go out that many at a time, the answers are used in the order of the features or use cases, so the result is the same as one at a time; a failure keeps the units before it),
  `llm.batch_chars` (default 6000, 0 = off) batches small files, and `generate` prints
  `estimate_repo_map`'s expected calls first.
- **Token accounting**: `generate`, `roles`, `glossary`, `entry-points` and `actors` end with a recap of calls, tokens
  and time per pass (and the prompt tokens the server served from its cache, shown only when one reported any, TOK-4/5), plus the answers a pass could not parse and the units it skipped (`LlmProvider::note_unparseable_answer`, sent by `complete_json`; tokens only, no prices) and append the run to `.retrodoc/cache/usage.json`; kept apart from the
  rendered docs so reruns stay no-ops, and left alone by `generate --force`. `commands/usage.rs` builds the providers
  (`PassProviders`, `pass_provider`) the commands use.
- `retrodoc_llm::HeartbeatProvider` (wrapped around the provider in the CLI) logs "still waiting for the
  LLM (Ns)" every 30 s, to tell a slow call from a stuck run.
