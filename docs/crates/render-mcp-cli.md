# Crates: render, mcp, web and cli

Detail moved out of `CLAUDE.md`. Overview: `docs/ARCHITECTURE.md` §3, §6 and §9.

- **retrodoc-render**: writes the Markdown/Mermaid output to the docs dir (`output.docs_dir`). Modules: `markdown/`
  (the entry points, paths and links in `mod.rs`; one file per page: `agent_index.rs`, `domain.rs`, `feature.rs`,
  `use_case.rs`; the tests by topic in `tests/`), `rules.rs`, `doc_links.rs`, `texts.rs`, `plan.rs`. `render()` builds
  the files in memory (deterministic), `plan()` compares them with the disk (created/updated + unified diff,
  a page under `functional/` the run no longer produces is `removed` when it still has the hash recorded in
  `_retrodoc/rendered-pages.json` (`RENDERED_PAGES_PATH`, written by `plan` with the other files), else `stale`:
  reported, never deleted; `specs/docs-pruning.md`), `WritePlan::apply()` writes only what differs, removes the
  `removed` pages and the folders they leave empty.
  `_retrodoc/run-metadata.json` has a timestamp that is ignored when it's the only change, so reruns are no-ops. `functional/llms.txt` (`agent_index`) is the `llms.txt`-style entry point for agents that don't
  run the MCP server: domains and features with links and confidence, how to read them and a pointer to `retrodoc mcp`.
  Its lists and those of the domain and feature pages share one item (`list_item`: link, score with ⚠️ below
  `LOW_CONFIDENCE_THRESHOLD`, name and description on one line; `specs/markdown-render.md`).
  A slug becomes a path segment of `[a-z0-9_-]` (`segment`, also the guard against `..`); two items whose slugs fold
  into one path fail the render (`RenderError::PathCollision`) rather than one page overwriting the other.
  The CLI drops generated docs (`functional/`, `_retrodoc/`) from the ingested existing docs.
  The CLI (`commands::docs::publish`, behind `render` and `generate`) renders the sections with the human edits of
  `.retrodoc/edits.json` laid over them (`retrodoc_mcp::edits::apply`, `specs/section-edit.md` SED-30 to SED-32): the
  render crate never sees an edit, only an `EditMark` per edited section (`edit_marks.rs`: the fields it changes, its
  author, its date, keyed by `ItemRef`), which writes `**Human edit** name *by A, <date>*` on the line under the
  heading of its page (SED-38), in the words the web page reads from the same `Texts` (`human_edit`,
  `edited_fields`, `edited_by`); a file of edits that can't be read fails the command before any doc is written,
  and `generate` before its first LLM call.
  The fixed text of the pages (headings, labels, notes, `llms.txt`, `rules.md`) comes from a `Texts` table
  (`texts.rs`, `specs/docs-language.md` DLG-7): `Texts::ENGLISH` and `Texts::FRENCH`, picked by `Texts::for_tag` from
  `OutputConfig::language_tag`, English for any language with no table; paths and anchors don't change with it.
  `render` and `render_with_rules` write English, `render_with_docs` takes the table.
  The rules the web interface shares with the pages are public: `Texts` (`technical_heading` / `technical_note`,
  `kind` for a rule's kind), `anchor` (a heading's anchor), `source_ref_label` (cited lines, `path:start-end`, the lower line first through `SourceRef::lines`, which the MCP answers and the web links read too), `DocLinks::of`.
  `render_with_docs` (`doc_links.rs`, `specs/docs-reconciliation.md`) adds, from the reconciliation of the debt report (`DocLinks`, built by the CLI's `doc_links`), an "Existing documentation" section to the page of each domain, feature and use case that a doc section documents or contradicts (relative link from the page to the doc file, anchor of the heading, `⚠️ states otherwise: …` for a contradiction), and an `Existing doc:` line under a rule on the feature and use case pages (not for a rule that cites the section in its evidence already). No link: the files of `render_with_rules`.
  What is not the core of the business is set apart (`issues/done/technical_and_back_office_use_cases.md`): on a feature page, the use cases for which `UseCase::is_technical` holds (the feature is `back_office`, business language under 0.8 or confidence under 0.6; a score not computed yet is no reason) go under "Administration and technical" after the business ones; a `back_office` feature (set by the features pass) is listed under that heading in its domain page and in `llms.txt`, not among the features. Nothing is dropped: the pages and the cache keep them all. The MCP answers keep everything and mark it: `get_feature` and `get_use_case` say so, and a list or a search result carries `[administration/technical]` (no change of ranking). The debt report says how many use cases and back-office features are set apart. The features the features pass marked technical are not set apart but left out (`features-set-aside.yaml`, never in `features.yaml`): `generate` and `report` list them per domain under "Technical features set aside". A domain no feature belongs to (named for entities alone, or with every feature set aside) gets no page, no entry in `llms.txt`, the MCP server and the web interface, and is not reconciled with the project docs (`DomainMap::published`, used by `domain_models` and the reconciliation items; `specs/featureless-domains.md`); the debt report lists it under "Domains with no feature" with the number of its features set aside.
- **retrodoc-mcp** (`audit/`, `corpus.rs`, `debt/`, `edits/`, `history/`, `reviews/`, `store.rs`, `search.rs`, `freshness.rs`, `source.rs`, `read_model.rs`, `tools/` (`Docs` in `mod.rs`, one file per tool named after it, the pieces the answers share in `answer.rs`, the review of a section in `review.rs`, the tests in `tests.rs`), `server.rs`): read-only access to the generated docs
  for LLM agents, with no LLM call (see `issues/done/mcp_server.md`). `SearchIndex` ranks (the hand-written BM25 of `retrodoc-pipeline`'s `bm25.rs`, shared with the pipeline, title counted
  three times, stop words in English and French dropped, at least half of the query words must match, and those
  matched must hold more than half of the query's IDF weight, `Bm25::search_relevant`, `specs/docs-search.md`, so an entry
  sharing only the common words of a question is left out; the not-documented answer counts those and names the query
  words no entry has) one `Entry` per
  domain, feature, use case, glossary concept and collected Markdown doc, each with its id, confidence and
  cited files. `GeneratedDocs` (`read_model.rs`, `GeneratedDocs::load` reads `.retrodoc/cache/`, business rules and glossary included, + the collected docs, then shows the edits of `.retrodoc/edits.json` over the sections, `GeneratedDocs::with_edits`: none, with a warning, when the file can't be read) is the typed read model, independent of how it is answered (ADR 0039); it keeps, read once, what the docs leave out (`Uncovered`: the reconciliation of the items with the collected docs from the saved verdicts, set by `GeneratedDocs::reconciled` (`retrodoc ui` only: `retrodoc mcp` does not read it), `None` with no collected doc; the files of the "uncategorized" bucket of `domains.yaml`, the files the budget left out of `scope.yaml`, `behaviour-coverage.yaml`); `debt::debt` lists from it the sections that need a human (`specs/debt-view.md`): those of the debt report's `build_report` (low confidence, not scored, unbacked narrative, technical language, set apart) and the stale ones, judged at each call, then from `Uncovered` the items the reconciliation finds contradicted or undocumented, the domains, features and use cases of the `Reviews` it is given marked wrong or to review (their comment as the rationale), those whose edit is outdated (`edits::outdated`, `DebtKind::OutdatedEdit`, with its `Outdated`), and the code no doc covers (entry points without a feature, files with no domain, reached by no behaviour, not analysed), one `Folder` item per kind and directory; a feature or use case validated by a review that is not outdated (`reviews::outdated`) leaves the four kinds that judge it, and an item marked wrong or to review carries the `Outdated` of its review (low confidence, not scored, unbacked narrative, technical language); each item's `Subject` is a section, a domain, a doc item or a folder; the list is sorted by each item's `Priority` (`weight × weakness × (1 + ln(1 + commits)) × (1 + ln(1 + entry points))`, the weight of its kind by tier, `DebtKind::weight`, the order by kind breaking ties), the commits those of the busiest of the item's files from the churn per file `GeneratedDocs::with_churn` sets (`GeneratedDocs::with_history` reads it in one revwalk, `retrodoc ui` only; none set: 0 commits); `audit::audit` gives the figures of the audit page (`specs/audit-dashboard.md`): the overall scores of the report, the entry point coverage of `behaviour-coverage.yaml`, the stale share, the last `generate` of `usage.json`, the contexts done as `fingerprints.json` records them (`retrodoc_pipeline::recorded_progress`), the domains, features and use cases of the run the `Reviews` it is given review, by status, and how many of those reviews are outdated (`Reviewed`), and the debt items counted by domain and kind (`DebtKind::WITH_DOMAIN`, the folder kinds have no domain) with a level from 0 to 4; `history` builds the snapshot of a run from the same report and debt (`specs/run-history.md`, ADR 0043): the commit, the end date, the cost summed from its `RunUsage`, the overall scores, the entry point coverage, the debt counted by kind (`DebtKind::key`, the `?kind=` of the debt page) and domain without the stale items, with the reviews `reviews.json` holds when the run ends (none, with a warning, when it can't be read), and the scores of every domain, feature and use case; `history::save` writes it as one new file under `.retrodoc/cache/history/` named by the end date (written aside then hard-linked, never over a saved one), none when it equals the newest file but for the commit, the date and the cost, and `history::load` reads them back oldest first, each named by its file (`SavedRun`), skipping a file unreadable or of a later `VERSION`; `history::diff` gives what one run changed in the sections of another (`specs/history-page.md`): the sections added and removed by kind and id, those whose confidence or business language fell by at least `FALL_THRESHOLD` (0.2, the p90 of the jitter of two runs of the same code), and the use cases newly or no longer set apart; `reviews` keeps the human reviews of the domains, features and use cases (`specs/section-review.md`, ADR 0044), its one write outside a run: `reviews::record` sets the review of a `Section` (kind and id of the history) the docs hold, with its `Status`, comment, the git `user.name` as author (`retrodoc_ingest::git_history::user_name`), the UTC date, the `fingerprint` of the section (the hash of its saved JSON) and the hash of each file the section cites (`files`), replacing the former one, `reviews::remove` drops it, and both save `.retrodoc/reviews.json` whole aside then renamed, by kind then id, one save at a time in a process (`store`, the load and save of the files of human work under `.retrodoc/`, generic over the `Record` of a section); `reviews::load` reports a file unreadable or of a later `VERSION`, and neither writer replaces it, and keeps the newest review of a section a merged file holds twice; `reviews::outdated` judges at each read whether a review still vouches for its section (`Outdated`: rewritten, its fingerprint differs; or the cited files modified or deleted since, `freshness::state_against`, only those the section cites now, `reviews::cited_paths`, which the debt also counts the commits of: a path of `reviews.json` is never read otherwise), never saved; `edits` keeps the human edits of the same sections (`specs/section-edit.md`, ADR 0045), an overlay the artifacts never hold: `edits::record` sets the `Fields` a human changed (name, description, the narrative of a use case only; none given or a blank one refused, `EditsError`), with the author, the UTC date, the `fingerprint` of the generated section and the hashes of its cited files (`reviews::cited_hashes`), replacing the former edit whole, `edits::remove` drops it, both through the same `store` as the reviews into `.retrodoc/edits.json`; `edits::fields_in` gives the name, the description and the narrative of a section in the shown or the generated `Sections` (the edit form fills and compares with them); `edits::outdated` judges at each read whether an edit still corrects its section, by the rule of the reviews (`reviews::judge`) against the section as generated, not as shown (SED-34 to SED-36); the readers name only the fields it changes as shown (`Edit::changed`: no blank field nor a narrative outside a use case, which a file written by hand may hold), and an edit with none is neither shown nor debt; `edits::Live` keeps the docs of a running server (`retrodoc ui`, `retrodoc mcp`) up to date: it reads the file at each request and rebuilds the docs only when its content changed and the edits it holds differ from those shown (SED-27, SED-28), under one lock, so a request waits for a rebuild in progress; `edits::apply` lays them over the `Sections` (domains, features, use cases), each field an edit gives replacing the generated one, an edit of a section the docs no longer hold and a blank field written by hand left out: `GeneratedDocs` answers with the shown sections (`domains()`, `features()`, `use_cases()`, `sections()`, the search index over them, `corpus::section_entries`) and keeps the generated ones (`generated()`), which `edits::record` fingerprints while a review fingerprints the shown section (an edit outdates it) and the reconciliation reads (its verdicts judged the generated text); `Docs` wraps it with the bounded source access and answers the seven tools in Markdown
  (`list_domains`, `get_domain`, `get_feature`, `get_use_case`, `search_docs`, `read_source`, `git_log`): ids to reuse, confidence (flagged below
  50%), cited files, a stale warning when a cited file no longer matches the hash recorded in `source-hashes.json` (`SourceHashes`, written only by a `generate` that went through every pass, hashes read before the features)
  (`Freshness`, checked at every call; files without a recorded hash are not judged), in `get_domain`, `get_feature` and `get_use_case` the human review of the section under its confidence, with why it is outdated when it is (`reviews::outdated`, `Outdated::reasons`), and, for one marked wrong, a warning before the title that says when the section changed since (`tools/review.rs`, `.retrodoc/reviews.json` read at each answer, its error said in place of the review), then the edit of the section, when it has one, on the next line (`Edit: human edit of …`, its author and date, why it is outdated when it is, `edits::outdated`, `Outdated::edit_reasons`) and, for an outdated one, the text the last run generated for each field it changes at the end of the answer (`tools/edit.rs`), and "Not documented" as a normal answer for an unknown id or an empty search; an id resolves only when every segment given matches, a slug alone when it is unambiguous (`specs/mcp-server.md`). `server.rs` puts them
  behind the `rmcp` SDK (`serve_stdio`); tested end to end with an `rmcp` client over an in-memory pipe. `source.rs` (`SourceAccess`) backs `read_source` (a
  window of lines, 200 by default, 400 at most) and `git_log` (hash, date, subject, no author): only files the docs
  cite, never an absolute path, a `..`, a path that is or goes through a symlink (even inside the repo), a binary or a
  file over 1 MiB; a line over 400 characters is cut. `git_log` leaves merge commits out and follows the renames of the file (`specs/file-history.md`), marking the commit
  that renamed it. The two tools run in
  `spawn_blocking`. `SourceAccess` returns typed data (`window`: a `Window` of numbered `Line`s; `commits`: `FileCommit`s;
  a `SourceError` per refusal) that the tools lay out in Markdown and the web interface in HTML; the set of cited
  files is `GeneratedDocs::cited_paths`.
